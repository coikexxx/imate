### Task 1: 设置存储与生效

**接口：** `get_runtime_settings`、`save_runtime_settings(settings)`；复用 `assistant_cli` 键，运行与调度配置分别保存为有默认值的对象。在一个事务中验证并保存，失败不写任何字段。已有网络代理、Dsh 设置继续走各自入口。

建议用以下类型承载现有默认值，全部使用 camelCase 串行化；与 `RunnerConfig.stdout_close_grace` 无关的内部清理参数保持默认。

```rust
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
#[serde(rename_all = "camelCase", default)]
pub struct RuntimeLimits {
    pub discuss_rounds: u32,
    pub reworks_per_task: u32,
    pub turns_per_instruction: u32,
    pub model_idle_seconds: u64,
    pub discuss_tool_seconds: u64,
    pub execute_tool_seconds: u64,
    pub discuss_total_seconds: u64,
    pub execute_total_seconds: u64,
}

impl Default for RuntimeLimits {
    fn default() -> Self {
        Self {
            discuss_rounds: 3,
            reworks_per_task: 2,
            turns_per_instruction: 30,
            model_idle_seconds: 300,
            discuss_tool_seconds: 600,
            execute_tool_seconds: 1_800,
            discuss_total_seconds: 600,
            execute_total_seconds: 1_800,
        }
    }
}
```

- [x] Step 1: 编写测试：无设置时返回上述默认值；无效数字、未知助理 CLI 或损坏设置不生效；同时提交两个字段的失败保存全部回滚。窗口显示的单位是分钟或回合，API 接收整秒和整回合。确认用例在实现前失败。
- [x] Step 2: 实现存储和 `RuntimeLimits -> RunnerConfig` 转换；起草、点名和团队 runner 使用同一份设置快照。团队首次启动把限制写入指令快照，派工、插话、重试、协议纠错、会话重建、重启恢复沿用；旧快照缺字段时使用原默认值。回合额度预留与提示词剩余次数使用同一个上限，返工协议校验与手动返工路径也共用。
- [x] Step 3: 测试运行中修改设置不会重置进行中的额度，新指令使用新值；定时器测试确认持续输出不能绕过总时长。执行 `cargo test --manifest-path src-tauri/Cargo.toml -- --test-threads=1`，通过后本地提交 `feat: 持久化运行设置并按指令冻结护栏`。

Task 1 实施记录（2026-11-17，Windows 11）：新增 `runtime_settings.rs`，键为 `assistant_cli`（纯字符串，空即自动选择）与 `runtime_limits`（camelCase JSON 对象，缺字段补默认值；损坏或越界时读取报错、运行时回退默认值）。`advance` 在指令 `turn_count == 0` 时把当前护栏冻结进 `context_snapshot_json.limits`，讨论阶段重置快照时保留；`TurnSpec.limits` 供团队 runner 取超时，空闲点名与助理起草在启动时各读一次。`TURN_LIMIT`、协议里的 3 轮／2 次与提示词里的 `MAX_DISCUSS_ROUNDS` 常量全部改读冻结值，文案随上限变化；旧指令快照缺字段时沿用 3／2／30 与原超时。验证：`cargo test --lib -- --test-threads=1` 352 passed、2 ignored（新增 10 项：存储 7 项、协议 1 项、提示词 1 项、编排冻结与旧快照 2 项、runner 持续输出不延长总时长 1 项，其中 `commands` 既有 2 项因名称含 limits 一并计入筛选），`cargo build` 通过。

### Task 2: 设置窗口与错误文案

**接口：** 设置页加载 `getRuntimeSettings` 和已探测的 CLI；保存成功更新页面，保存失败保留草稿和原设置。空助理选择显示「自动选择」，选择项显示安装、接入状态。项目页保留现有网络代理和 Dsh 设置入口。

- [ ] Step 1: 加入设置路由和入口，使用既有输入组件。用户提交前就能看到取值、单位、生效时机和未安装 CLI 的提示。为加载失败、非法输入和保存后重开编写状态用例；执行前端测试确认期望失败。
- [ ] Step 2: 展示现有结构化状态能确认的错误：CLI 不可用、回合超时、用户停止、等待清理、回合失败。上下文已自动重开且成功时不留失败提醒；权限或上游失败不能被改写成成功；未知错误显示既有可安全公开的诊断，不解析或显示原始 stderr。界面短提示和 `runs.error` 保持区分。
- [ ] Step 3: 窗口验证设置保存后重启可见；未安装 CLI 显示明确原因；停止、超时、清理与普通失败各自有正确入口。跑 `npm test`、`npm run build`。本地提交 `feat: 添加设置窗口并明确运行错误文案`。

### Task 3: 按项目展示用量

**接口：** `get_project_usage(project_id)` 只接受项目 ID，按成员及项目汇总 `runs.usage_json`。返回成功记录数、有用量记录数、每项的数值与覆盖范围。不读 CLI 日志，不把累计 `rawUsage` 当成单次费用。

- [ ] Step 1: 建立两项目的隔离测试：含已知数值、已知零、缺字段和整条未知用量；验证缓存不重复计入，项目不会串账，失败或中断回合显示覆盖不足。记录归一字段相加时的选择：各输入字段分列；无证据的合计字段保持空。
- [ ] Step 2: 在项目页放「用量」区域。每次回合完成刷新一次，切换项目时丢弃旧响应。未知显示「未报告」，部分已知标注「已报告的合计」，只有有证据的费用显示金额。明确不设费用硬上限，也不按 token 估算未知费用。
- [ ] Step 3: 运行真实团队指令，对照该指令的 `runs` 核对窗口数值。至少覆盖一种有真实用量和一种不提供费用的 CLI。运行后端串行测试、前端测试与构建，本地提交 `feat: 展示项目用量与覆盖范围`。

### Task 4: macOS / Windows 安装包与干净机验收

**接口：** 两平台从同一个 Git 提交和锁文件构建，产物本地保留版本、目标架构和 SHA-256。macOS 产出 DMG，Windows 产出 NSIS 安装程序。开发验收与正式签名发布分别记载；正式发布所需签名、公证、证书或对外上传由用户确认后另做。

- [ ] Step 1: 在 macOS 与 Windows 各自的本机构建环境执行 `npm ci`、`npm test`、`npm run build` 和后端串行测试。macOS 执行 `npm run tauri build -- --bundles dmg`；Windows 执行 `npm run tauri build -- --bundles nsis`。写下构建机架构、系统、产物校验和，任何失败保留实际诊断。
- [ ] Step 2: 在两台干净环境分别安装。先在没有 CLI 的环境验证首页和引导可用，再安装并登录一个已接入的 CLI，走「新建项目 → 配规章与成员 → 点名 → 团队交付 → 停止 → 重启并保留数据」。应用已安装、CLI 已安装、CLI 已登录是三件不同的事。验证 Finder/Dock 或开始菜单的启动；从开发环境启动不计入本项。
- [ ] Step 3: 记录无法验收的平台、签名状态及还没接入的 CLI，更新 README、手册和进度。只在真实安装门通过后标记对应平台完成。保留 M2 已暂缓的独立验收记录，不把安装成功替代为工具层或残留进程验收。本地提交 `docs: 记录双平台安装包与干净机验收`。

**确认项：** 是否按上述设置生效规则、用量口径及 DMG/NSIS 产物开工。macOS 可先做本机验证；Windows 构建与两平台干净机需要相应环境。尚未提供正式签名与公证材料，不在本计划确认之前生成发布产物或上传。
