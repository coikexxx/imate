## 1. imates 现状（评审基准）

Tauri 2 桌面应用（Rust 后端 + 前端），目标平台 Windows 11。每个 Agent 由本地 CLI（claude、codex、grok、dsh、pi）的**无头进程**驱动，按"组长负责制"协作。

手册第 4 节的核心设计：

- **组长指令协议**：组长回复末尾带 `imates` 代码块，内含 JSON，`action` 取 `reply` / `discuss` / `assign` / `rework`。解析失败把错误发回组长，只重试一次；仍失败原文当普通发言，指令置为"等待用户"。
- **流程**：组长研判 → `discuss`（成员**并行**发言，最多 3 轮）→ 组长裁定 → `assign`（成员串行执行）→ 组长验收 → `reply` 交付，或 `rework`（每任务最多 2 次）。
- 讨论模式只读，执行模式可写；各 CLI 用自身只读参数，没有只读模式的靠提示词兜底。
- 上下文：每个 Agent 记 `last_seen_message_id`，只发新消息。
- 用户干预：停止、插话（入队）、`@成员` 绕过组长。
- 异常（第 9 节）：成员失败记"未发言"；回合超时默认 10 分钟杀进程树；重启后 running 标 interrupted；失败**不自动重试**。
- MVP 不做：并行执行、危险操作审批、Agent 互相喊话。

进度：M1 骨架代码完成，M0（CLI 实测）和 M2（单 Agent 对话）未开始，M3 计划未写。

## 2. 参考项目

### 2.1 The Pair — 适配器层的最佳参考（技术栈同为 Tauri 2 + Rust）

- Apache-2.0，约 387 星，三平台。两个 Agent 结对：只读的 Mentor 规划和验收，Executor 写代码。支持 10 种 CLI。
- **读过的文件**：`providers/claude.rs`（前 330 行）、`providers/codex.rs`（前 250 行）、`provider_adapter.rs`（前 130 行）、`process_spawner.rs`（常量、`kill_process_tree`、`await_turn_exit`、Windows 启动器处理）、`message_broker.rs`（停滞监控）、`acceptance.rs`（JSON 提取、校验、提示词）、`pair_manager.rs`（恢复提示词）。**没读**：其余 8 个 CLI 的适配器、会话快照、worktree 管理、前端。

**对 M0 / M2 直接有用的实测知识**（来自代码注释，作者标注了在具体 CLI 版本上验证过）：

| CLI | 无头调用（The Pair） | 踩过的坑 |
|---|---|---|
| claude | `claude -p --verbose --model M --output-format stream-json --permission-mode plan\|auto [--resume SID] [--effort E] -- <prompt>` | ① 消息以 `-` 开头（如 markdown 列表、`---` diff）会被当选项，turn 在任何 JSON 事件前以 exit 1 退出，必须加 `--` 隔开。② `system/init` 事件里的 `permissionMode` 若是 `default`/`manual`，说明请求的 `auto`/`plan` 没生效（模型或账号不支持），此时编辑全被拒绝**但结果仍报成功**。③ 结果事件 `result.usage` 是**本回合**用量，不是会话累计；`input_tokens` 只含未缓存部分，需加上 `cache_creation_input_tokens` 与 `cache_read_input_tokens`。④ 错误回合是 `result` 事件带 `is_error` 或 `subtype` 以 `error` 开头；还有 `permission_denials` 数组。⑤ 登录是 `claude auth login`，`claude login` 会被当 prompt。 |
| codex | `codex exec [resume SID] --skip-git-repo-check --model M -c sandbox_mode="read-only\|workspace-write" [-c approval_policy="never"] [-c model_reasoning_effort=E] --json --output-last-message FILE -- <prompt>` | ① 不在 git 仓库里会拒绝启动，需 `--skip-git-repo-check`。② `exec resume` **不接受 `--sandbox`**，只能用 `-c sandbox_mode=`。③ 用户 `config.toml` 里若是 `approval_policy="on-request"`，无头执行者会卡在永远没人回答的审批上，需显式写 `never`（沙盒才是真边界）。④ 终止事件是 `turn.completed`，失败是 `turn.failed`，`error.message` 里可能嵌套一层 JSON。⑤ **自 0.154 起 `turn.completed.usage` 是线程累计值**，resume 后要减去基线才得到本回合用量，且 codex 的缓存字段是 input 的子集，不能再相加。⑥ 最终回复可用 `--output-last-message` 写文件取回。 |

**进程管理（`process_spawner.rs`）**：
- 杀进程树：Unix 用进程组 SIGTERM，2 秒后 SIGKILL；Windows 用 `taskkill /T /F /PID` 并带 `CREATE_NO_WINDOW`。原因是 npm 启动器会再起 Node 进程和真实二进制。
- stdout 关闭后等进程退出最多 30 秒，超时则杀掉，并**标记输出被截断，不能当作完成的回合**。
- 回合空闲超时 30 分钟（无任何 stdout 行才算）；另有监控任务每 5 秒采样，停滞 120 秒告警、600 秒严重。
- **Windows 特有问题**：npm 的 `.cmd` 启动器无法接收多行 prompt。代码会解析 npm shim，直接用 `node.exe 入口脚本` 启动；找不到时报错"请用 npm 重装或使用原生 .exe"。**imates 的 `dsh` 只有 `.cmd` 垫片，会撞上这个问题。**
- 抓取的每回合 stderr 只保留尾部 40 行用于报错。

**适配器抽象**：`Provider` trait + `ProviderRuntimeSpec`（输入/输出传输、会话策略 NewFirst/ResumeExisting、权限策略 Auto/PreApproved/ManualConfirm、工作目录策略）；每个 CLI 实现 `build_turn_command`、`extract_token_usage`、`extract_error_detail`、`final_output_text` 等。

**验收与回合控制**（`acceptance.rs`）：
- Mentor 返回 JSON verdict：`verdict`(pass/fail)、`risk`、`confidence`、`issues`、`evidence`、`reasoning`、`summary`、`nextStep{action: continue|finish, instructions[]}`。
- 提取 JSON 的方式：整段原文、去代码围栏、再**扫描每个 `{` 的括号配对（感知字符串和转义）**逐个尝试；先严格解析再宽松解析。
- 校验自洽性：`continue` 必须带 instructions；`finish` 不能带；`fail` 必须配 `continue`（否则循环无下一步）；`finish` 需 `confidence ≥ 0.8`；`pass` + `continue` 合法（多步任务中某步正确但未完成）。校验失败 → 把解析错误发回 Mentor，用专门的"修复提示词"重试，记 `repair_attempts`。
- 风险等级 `risk` 由代码按**改动文件**分类，不完全信模型自述。
- 角色硬隔离：Executor 提示词写明"你不能宣布完成，只有 reviewer 能结束工作流，不要输出 TASK_COMPLETE"。

**局限**：只有 Mentor / Executor 两个固定角色，没有多人讨论。

### 2.2 Meldwork — 讨论层的主要参考

- Apache-2.0，约 1.5k 星，Electron，目前仅 macOS。13 种 Agent CLI 的自动讨论与互审。
- **读过的文件**：`natural-discussion-prompt.cjs`（全文）、`local-workspace-auto-runner-natural-discussion.cjs`（全文）、`-natural-decisions.cjs`（全文）、`-natural-consensus.cjs`（全文）、`task-decision.cjs`（全文）、`invocation-watchdog.cjs`（全文）、`failure-policy.cjs`（分类与重试决策）、`cli-invocations.cjs`（codex/claude/qwen/gemini 调用）、`cli-adapters.cjs`（`runAgent` 开头）、README、`architecture.md`。**没读**：V4 阶段调度（`orchestration-v4-records.cjs` 等）、Run Ledger、Human Gate、各 CLI 事件解析器。

**它有两种讨论风格，其中 `sequential`（顺序）最接近 imates**：每轮所有活跃成员**依次**发言，一个 owner（默认第一个参与者）在每轮结束时给出任务判定。`agent-led` 风格由 Agent 用 `nextKinds` 点名下一个发言者。

**`sequential` 每轮结束后的决策逻辑**（`v4NaturalRoundOutcome`，这是最值得对照 imates 第 4 节的部分）：
1. owner 失败或被暂停 → 下一位活跃参与者**自动接任** owner，并发系统消息说明。
2. 点名的成员不在场 → **丢弃该条点名**并提示，不终止讨论（旧版本曾因此整体终止，被作为 bug 修掉）。
3. 同伴报告 `blocked` / `needs-human` → **转交 owner 裁定**，不直接终止。
4. owner 没给读得懂的判定 → **追问一次**；上一次也缺失才停止，状态为 `partial`。
5. owner 宣布 `completed`，但同伴还没有过独立的讨论轮 → **强制再跑一轮交叉评审**，避免整轮坍缩成 owner 一人自审。
6. owner 在有成员中途失败的情况下宣布完成 → 结果是 `partial` 而不是 `completed`，并说明缺了谁。
7. `needs-human` → 向用户请求决定；批准则回到 owner，拒绝则停止。
8. **重复检测**：窗口 `max(4, 2×人数)` 轮内，每个 Agent 的归一化内容（去 @、压空白）加交付文件哈希完全不变 → 判定"无新贡献"，停止并提示。
9. 轮数上限默认 6，可设为无限。

**回执解析**（`task-decision.cjs`）：先 `normalizeTaskDecision` 再严格校验。归一化包括：状态同义词（`done`/`finished`/`success` → `completed`，`in-progress`/`pending` → `continue`，`needs human` 等）、去掉 `@`、单个字符串转数组、`completed` 无交付物时补默认值"本条消息中的回答"、`reason` 缺失时用摘要代替。严格校验限长（reason 1600、交付物 ≤16 条各 ≤800）、拒绝控制字符、对文本做密钥脱敏。回执不可读 = 当作"没有判定"，而不是让该 Agent 失败。

**完成判定**（`natural-consensus.cjs`，仅 agent-led 风格使用）：候选版本 = 提议消息文本 + 交付文件的 SHA-256；全部目标成员必须用 `reviewedVersion` 批准同一哈希；任何 `continue` 判定撤回候选；**批准状态从持久化消息重建**，崩溃后不丢；交付文件被外部改动（大小或哈希变化）则候选作废。

**看门狗**（`invocation-watchdog.cjs`）三个窗口：启动期（严格回合必须在 `timeoutMs` 内出现任何活动迹象）、无活动期（任何进展刷新窗口，工具调用期间用更长的 `toolTimeoutMs`）、停滞期（严格回合在 3 个窗口内没有"实质进展"也终止）。区分 `liveness`（进程有 stdout/stderr 字节）与 `progress`（映射后的事件、回答文本、工具生命周期）。等待人工决定时 `pause()`，不算 Agent 静默。

**失败分类与重试**（`failure-policy.cjs`）：12 类（authentication、compatibility、session、rate_limit、network、provider、timeout、cancellation、permission、budget、protocol、execution）。只有**明确的登录语句**才算认证失败；403、代理拒绝、输出中恰好出现 "unauthorized" 都按 provider 失败重试。可重试类别：rate_limit、network、provider、timeout、protocol，最多 4 次；会话失效类最多 2 次并先刷新会话；认证和兼容性类绝不重试。从 CLI 文本里解析 `retry after 20s`。**若失败时可能已有副作用且操作不幂等 → 不自动重试，转人工确认**。

**中断恢复**：一个可写的 Agent 被中断且结果未知时，不自动重试，请求用户"重试一次 / 不重试"（因为它可能已经改了文件）。

**CLI 调用差异**（`cli-invocations.cjs`）：Meldwork 通过 **stdin 传 prompt**（codex 用 `-`），The Pair 用 `--` 加位置参数；两种都能避开"以 `-` 开头被当选项"。Claude 讨论模式用 `--permission-mode plan`，可写用 `acceptEdits`；codex 恢复会话用 `exec resume --json --skip-git-repo-check -c sandbox_mode=...`，首次用 `--sandbox` 与 `-C workdir`。默认沙盒 `read-only`。

**提示词**（`natural-discussion-prompt.cjs`）：明确写"本次调用只是一次发言，调度由应用负责，不要等同伴、不要轮询文件"；"把当前用户任务视为权威，旧计划和旧回复只是参考，不是待办"；owner 提示词要求宣布完成前让相关同伴审过真实交付物；"同伴沉默不算完成的证据"。

**局限**：回执靠 prompt 约束，Agent 不听话时只靠容错兜底；V4 部分代码量巨大（`orchestration-v4-records.cjs` 122KB）；仅 macOS。

### 2.3 Orkas — 最像"组长"的实现，但组长不是 CLI

- MIT，约 9.1k 星，Electron，macOS + Windows。Commander（指挥官）拆解目标，调度内置专家和用户已装的 Claude Code、Codex、OpenCode 等。有项目、待办、自动推进、定时任务。
- **读过的文件**：`prompts/chat_commander.md`、`chat_agent_in_group.md`、`dispatch_planner.md`（全文）、`group_chat/dispatch_planner.ts`、`plan_executor.ts`、`task_board.ts`（导出与状态）、`bus.ts`（准入循环、grep 关键字）、`local_agents/backends/base.ts`、`claude.ts`、`codex.ts`（头部与 grep）、`docs/test/agent-orchestration-regression.md`。**没读**：`bus.ts` 的大部分（555KB）、router、反思编排器、项目/自动推进/定时任务。

**关键机制**：
1. **Commander 是进程内的 LLM Agent，用工具调度**：`dispatch_to`（并行或需消费结果时用）、`hand_off_to`（一个 Agent 接管剩余结果，尤其是需要用户多轮回复的交互式 Agent）、`run_worker`（匿名、有界的批量扫描）。外部 CLI 是被调度的 worker；worker 用 `<handback reason="completed_handoff" />` 或 `reason="capability_boundary"` 把发言权交还。**这与 imates 让某个 CLI 当组长不同**，Commander 能直接调用工具，不必靠文本 JSON。
2. **派工计划的宿主侧校验**（`dispatch_planner.ts`）：一次结构化模型调用，宿主验证——负责人必须是被点名的成员或 Commander；1 到 8 个任务；`part` 非空；`after` 只能引用**更早**的任务（天然无环）；被点名的成员必须被分配或列入 `references`；20 秒超时。任何失败（超时、非 JSON、模型反问）回退到 Commander，**模型从不直接写任务板**。规划提示词里有细则：用户说"我自己来"的步骤不分配给任何人；"同时/各自/分别"的任务互不等待；拿不准时让任务等待（"等待只损失时间，提前开始会丢输入"）。
3. **依赖失败不级联取消**（`bus.ts` 准入循环）：任一前置任务以非 done 结束，该任务立即标为 `blocked` 并等用户决定，**不静默放行也不静默级联取消**。
4. **三道刹车**：会话回合上限 `MAX_WORKER_TURNS = 100`；任务 token 成本上限（超了丢弃队列并通知）；每会话并发任务数上限。
5. **任务状态 8 种**：queued、running、waiting_input、blocked、done、stopped、failed、cancelled；终态 4 种。
6. **Commander 提示词的设计原则**：同一责任范围内自己决定谁做、怎么拆、怎么验证，不问用户；只有真正需要用户输入或新授权时才问；"任务体量大不构成用多个 Agent 的理由，不要为了显得忙而派工"；派工只发"执行契约"（动作、交付物、验收标准、新增约束），Agent 自己有历史和附件；失败时**不重试已中止的运行**，基于证据恢复；替换了用户指定的 Agent 必须告知；恢复简报要写清症状、已保留的工作、剩余修复、所需证据、原始目标。
7. **恢复语义**（回归文档）："继续"复用已完成步骤的消息、文件、摘要，只重跑失败的步骤；用户定义的阶段批准门禁下，一次批准只推进一个阶段，"继续"不得被当成放弃门禁；项目中保存的默认规则可被当前请求明确覆盖，但不改动已存规则；待办、记忆、历史对话里的"指令样"文本只当记录不执行。
8. **CLI 驱动方式与 imates 不同**：它用**常驻进程 + 双向协议**——Claude 用 `stream-json` 输入输出并开 `--permission-prompt-tool stdio` 处理权限请求；Codex 用 `codex app-server --listen stdio://` 的 JSON-RPC（`thread/start`、`thread/resume`、`turn/start`）。有 `idleKillMs` 无进展杀进程、硬墙钟上限 `timeoutMs`、`StderrTail`、`killProcessTree`（Windows 用 `taskkill /t /f`）。`done` 事件状态：completed / failed / cancelled / timeout / missing_cli，并区分 `cli_spawn` 与 `cli_protocol` 失败、`retrySafe`。

### 2.4 OpenRig — 架构路线不同，只取思想

- Apache-2.0，约 8.8k 星，TypeScript。YAML 定义团队，一条命令启动，lead agent 协调。
- **读过的文件**：`README.md`、`ARCHITECTURE.md`（前 120 行）、`coordination-primitive.md`（第 1–3 节）、`adapters-and-runtimes.md`（grep 就绪检测）、`demo/` 示例。**没读**：任何 `.ts` 源码。

**要点**：
1. **在 tmux 里常驻交互式 TUI 会话**，Agent "不被修改"，靠 daemon 往里投递消息；需要 tmux、Node 22/24，macOS / Linux / WSL2，**不支持原生 Windows**。因为是交互式，要处理 `trust_gate`、`login_required`、`mcp_gate`、`update_gate` 等启动期弹窗，就绪检测靠探测 tmux 会话和历史。无头模式没有这类问题。
2. **SQLite 持久协调层**：`stream_items`（只追加）、`queue_items`（8 种状态）、`queue_transitions`（只追加的状态变更日志）、`inbox_entries`、`outbox_entries`，发送/接收均按 id 幂等。
3. **"hot-potato 闭合契约"**：一个队列项要进入 `done`，必须带 `closure_reason`（交接、拒绝、取消、无后续、升级、被取代）；交接和升级还必须带 `closure_target`；"交接并新建"在同一事务里完成。**不能静默地结束一件事，必须说清它去了哪。**
4. 会写用户的 `~/.codex/config.toml`、`~/.claude.json`、`~/.tmux.conf`；kernel 默认权限较宽（Codex `danger-full-access` 加 `never`）。

结论：架构与 imates 不匹配。可取的是"每个交接必须有闭合原因、状态转换只追加日志"的思想。

### 2.5 StarNet — 只与像素办公室、前后端契约有关

- MIT，约 1.8k 星，Windows / macOS。**读过的文件**：`README.md`、`CODE_MAP.md`（全文）。**没读源码**。
- 它**不驱动外部 CLI**：Node sidecar 内嵌在 Tauri 里，agent 循环在进程内，直接调模型 API，所以协作层无参考价值。
- 可借鉴的：
  - **前后端事件契约冻结**：`shared/events.js` 约 60 种事件类型，双向 schema 校验，"只增不改"。对应手册第 7 节 Event。
  - 像素世界用单个 canvas（`world.js` 约 5.6k 行），前端拥有名册，sidecar 镜像；"每个 crew 是独立运行，但只有主角会走动"——说明像素动画可以只做少数角色的移动，其余原地。
  - 产品原则："界面不得断言运行时无法证明的状态"。

## 4. 对 imates 手册的具体建议（按价值与成本）

> **采纳结果（2026-11-10）**：本节是调研当时的建议，对照的是手册第 2 版。评审后的取舍已写入手册第 3 版和 M0 计划，以手册为准。
>
> - 已采纳：第 1–6 条、第 12 条的"失败不自动重跑"部分；第 9 条简化为"无输出超时 + 总时长上限"两个超时；第 10 条简化为只区分"未登录"与其他，且只有组长回合自动重试一次。
> - 评审时新增（本节没有）：单条指令回合总数上限、并行讨论下消息游标的推进规则、任务失败后取消余下任务、会话续接失败后重开会话、交付时附注未完成的任务。
> - 未采纳：第 8 条里的"组长失败由成员接任"和重复检测；第 11 条（`messages.id` 自增已保证顺序）；三窗口看门狗；12 类失败分类；讨论由并行改顺序。
> - 第 7 条（验收前同伴复核）记入手册第 12 节候选项。

**A. 现在就该改手册（成本低，直接规避已知坑）**

1. **第 3 节 CLI 适配**：写入上面 2.1 的调用模板与坑位清单，作为 M0 实测要核对的清单，而不是凭印象。尤其：prompt 必须用 `--` 隔开或走 stdin；codex 恢复会话用 `-c sandbox_mode`；检查 claude 的 `permissionMode` 是否真的生效；codex 用量是累计值要减基线。
2. **Windows `.cmd` 垫片**：`dsh` 只有 `.cmd`，多行 prompt 会被截断。需在 M0 里验证 `dsh` 能否用 stdin，否则要解析垫片直接起 Node。
3. **杀进程树与"输出被截断"标记**：Windows 用 `taskkill /T /F`；stdout 关闭后等 30 秒再杀；这种回合不能算完成。
4. **组长指令解析**（第 4 节）：重试前先做归一化（同义词、尾逗号、智能引号），JSON 提取改为括号配对扫描；重试提示词带解析器的具体错误；`reply`/`assign`/`rework` 增加自洽校验（如 `assign` 的任务清单非空）。
5. **成员讨论提示词**加"本次调用只是一次发言，不要等同伴、不要轮询文件"；加"把当前用户指令视为权威，旧计划只是参考"。

**B. 应写入 M3 计划（改状态机，中等成本）**

6. **`assign` 任务清单的宿主侧校验**：数量上限、成员存在、依赖只能引用更早任务；任一前置任务失败则后续任务标 `blocked`，交组长或用户决定，不自动级联。
7. **验收前同伴复核**：组长宣布交付前，若涉及某成员边界，先 `discuss` 让其复核；组长在有成员失败的情况下交付时，结果标注缺了谁。
8. **每轮结束的决策规则**（上面 Meldwork 第 1–8 条）：组长失败时由谁接任、点名了不在场的人如何处理、成员报告阻塞如何转给组长、组长缺指令时追问一次、重复检测。
9. **三窗口看门狗**取代单一 10 分钟：启动期、无活动期、停滞期；区分"有字节输出"与"有实质进展"。
10. **失败分类**：至少区分认证 / 限流 / 网络 / 超时 / 协议 / 其他；认证失败要有"明确登录语句"的判据；限流解析 `retry after`；**可写 Agent 失败且结果未知时，不自动重试，问用户**。
11. 并行讨论轮的**消息顺序号**，在 Agent 启动前分配。
12. 恢复语义：重启后"继续"复用已完成任务，只重跑失败的。

**C. 建议先不做（记入第 12 节"MVP 之后"）**

- 并行独立提案（盲提案）；Agent 间互相点名（agent-led）。
- 候选版本哈希投票；Run Ledger；Human Gate 框架。
- 常驻进程 + 双向协议（Orkas 的方式）——它换来的是权限请求和中断能力，对应手册第 12 节的"危险操作审批"，MVP 阶段不需要。

**D. 明确不学**：tmux 驻留 TUI 会话（OpenRig）；进程内 Commander（Orkas）；SQLite 队列与 outbox（OpenRig）。
