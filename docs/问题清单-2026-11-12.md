## 2. 触发场景（可复现）

项目「M5 验收 2026-11-11」，成员：组长（Claude Code，模型 `opus`）、grok 成员（Grok，模型 `grok-4.7`）、dsh 成员（DeepSeek Harness，模型为 Dsh 选择 JSON）。

1. 用户发指令「Hallo-world里面增加一点粒子特效」。组长派给 grok 成员，grok 因 `Couldn't set model 'grok-4.7': Invalid params: "unknown model id"` 失败（当时 `grok models` 偶发地只返回 `grok-4.6`、`grok-4.5`，几分钟后又恢复了 `grok-4.7`，属上游的偶发现象）。组长改派给 dsh 成员，dsh 返回 `503 Service temporarily unavailable`（上游暂时不可用）。任务状态 `failed`，指令正常收尾（`completed`），系统消息列出未完成任务。
2. 用户接着发新指令「重试一下」（这是**新的一条指令**，`5523b6bb`，kind=team，phase=triage）。组长在 14 秒内回复，并在协议块里写了 `"action":"assign"`，其中 `replaces_task_id` 指向上一条指令里失败的任务 `226aadd2-…`。
3. 之后这次运行（`dd3391f3`）和这条指令一直停在 `running`，项目状态停在「讨论中」，组长显示「执行出错」，群聊里没有任何说明。用户再发「什么意思」，排进这条卡住的指令，没人回复。

## 3. 证据（来自应用数据库与 Claude 会话文件，只读查看）

- 数据库位置：`%APPDATA%\com.coike.imates\imates.db`（Windows）。关键记录：
  - `runs`：`dd3391f3` 的 `status='running'`、`ended_at` 为空，`reported_model='claude-opus-5-5'`（说明模型事件已处理），已运行 165 秒以上。
  - `instructions`：`5523b6bb` 的 `status='running'`、`phase='triage'`、`turn_count=1`。
  - `tasks`：`226aadd2` 属于指令 `bb44a9a8`（上一条），不属于 `5523b6bb`。
- 组长的 Claude 会话文件（`~/.claude/projects/<项目目录编码>/f519d7f8-….jsonl`）显示 Claude 在 18:56:14 已经 `end_turn`，输出了带 `replaces_task_id` 的协议块。
- 应用进程 `imates.exe` 的子进程里**没有任何 claude 进程**：CLI 早已结束，卡住的是应用自己的收尾。
- 终端（`npm run tauri dev`）没有任何错误输出：应用没有日志，错误只经 `run:finished` 事件的 `error` 字段短暂出现。

## 4. 根因链

1. `src-tauri/src/orchestrator/mod.rs` 的 `apply_leader` 处理 `ActionKind::Assign` 时调用 `instructions::insert_batch(...)?`。
2. `src-tauri/src/store/instructions.rs` 的 `insert_batch` 在事务里建好新任务后，对带 `replaces_task_id` 的项调用 `supersede_in`；`supersede_in` 要求被替代任务与新任务属于**同一条指令**，否则 `Err(invalid("只能替代同一条指令里的任务"))`。整批回滚。
3. 这个 `Err` 沿着 `apply_leader` 的 `?` 一路传出 `orchestrator::apply_outcome`。
4. `src-tauri/src/commands.rs` 里调用 `apply_outcome` 的位置（搜索 `crate::orchestrator::apply_outcome(&conn, &spec.run_id, &outcome)`）只是 `emit_run_finished(..., error)` 并 `halted = true`，**没有把运行终结、没有把指令转成 `waiting_user`、没有写系统消息**。数据库里运行与指令从此一直是 `running`。
5. 对比：协议本身不合格时有专门的恢复路径 `protocol_failed`（让组长重发一次）。但「`replaces_task_id` 指向别的指令的任务」属于**语义**错误，到写库才被发现，没有走这条路径。

## 5. 问题清单

### 问题 1（严重）：处理回合结果出错会让运行和指令永久卡在「运行中」

- 现象与根因：见上。任何 `apply_outcome` 的 `Err`（不只是本例）都会这样。
- 建议修法：在 `commands.rs` 调用 `apply_outcome` 失败时，走一个统一的兜底：把这次运行记为 `failed`（带错误文本）、把指令转成 `waiting_user`（`wait_reason` 写明原因）、项目状态回到可操作的状态，并在群聊里写一条**系统消息**说明失败原因，使界面出现「重试 / 补充 / 放弃」。可复用 `mark_waiting`、`finish_run_with`、`wait_instruction` 等已有函数；保持幂等（运行已不是 `running` 时不报错）。
- 验收：构造一个让 `apply_outcome` 必然失败的回合（例如组长回复里 `replaces_task_id` 指向别的指令的任务），断言：运行 `status='failed'` 且有 `error`；指令 `status='waiting_user'`；项目不是 `discussing`/`executing` 的卡死状态；群聊里有系统消息；`resume_instruction(..,"retry")` 能继续。

### 问题 2：`replaces_task_id` 的合法性应在协议校验阶段发现，让组长纠正

- 现状：`parse_final`（`orchestrator/protocol.rs`，带 `LimitContext`）只校验格式，不校验被替代任务是否存在、是否属于当前指令。
- 建议修法：把「被替代任务必须存在、属于当前指令、尚未被替代」的检查并入协议校验，失败走现有的 `protocol_failed`（让组长按提示重发一次，仍失败才转 `waiting_user`）。给 `LimitContext` 增加当前指令的任务集合或一个校验回调即可。
- 验收：协议单测——`replaces_task_id` 指向其他指令的任务、不存在的任务、已被替代的任务，均得到可读的协议错误；`apply_leader` 的集成测试——这种回复触发一次重发而不是卡住。

### 问题 3（已确认采用 B）：「重试一下」应该能替代上一条指令里失败的任务

- 现状：用户自然会用新的一句话说「重试一下」，这就是一条新指令；组长（合理地）想替代上一条指令里失败的任务，却被规则「只能替代同一条指令里的任务」拒绝。组长之所以拿到旧任务编号，是因为它的提示词里有上一条指令遗留的未完成任务（见系统消息「以下任务尚未完成」）。
- 原备选方向如下；2026-11-12 用户已确认采用 B，A 不实施：
  - A. 放宽 `supersede_in`：允许替代**同一项目里、状态为 `failed`/`cancelled`、尚未被替代**的旧任务（跨指令）。需要同步改 `creates_cycle` 的假设、手册里关于任务替代的描述，以及相关测试。
  - B. 不放宽，但在提示词里明确告诉组长「跨指令重试请新建任务，不要写 `replaces_task_id`」，并配合问题 2 的校验让它自我纠正。
- 验收：按选定方向补单测；窗口里复现「失败后发『重试一下』」能正常派工。

### 问题 4：Grok 在失败的运行上也「报告」了模型，消息旁显示有误导

- 现状：`adapters/grok.rs` 在 `system init` 里读出 `model` 并发出 `AgentEvent::ModelReported`；但 Grok 的 init 事件会**原样回显配置的模型**，随后才校验并报 `unknown model id`。所以失败的运行里 `reported_model='grok-4.7'`，群聊里显示的是「grok-4.7」，看起来像「实际用了 grok-4.7」，其实它根本没跑起来。（Claude 的 `claude/error.jsonl` 样本里 init 也回显了 `no-such-model`，同理。）
- 建议修法：让前端区分「运行成功」与「运行失败」：`ModelInfo` 增加运行状态（或布尔 `confirmed`），`modelNote` 对失败的运行只显示「xxx（请求值，运行失败，未确认）」。后端 `messages` 联表时一并带出 `runs.status`。成功运行仍显示报告值。Grok 成功时 `result` 事件里还有 `modelUsage`（实际计费的模型），可作为更可靠的报告来源，但不是必须。
- 验收：`modelNote` 单测；后端 `model_info` 序列化单测（含 `runStatus`）；窗口里 Grok 失败消息旁不再显示成「已报告」。

### 问题 5（建议暂缓，先记录）：瞬时错误没有自动重试

- 现状：Dsh 的 `503 Service temporarily unavailable`、Grok 偶发返回不完整的模型列表，一次失败就让组长改派，进而用户要手动重试。
- 建议：这是新功能，先评估现有重试逻辑（`protocol_failed` 的一次纠错、`rebuild_turn` 的一次重建）再设计：只对明确的瞬时类错误（5xx、`unknown model id` 且 `grok models` 此刻能列出该模型等）做至多一次自动重试，并在群聊里留痕。不要在没有设计的情况下直接加。
